## Decisions made during implementation

- **Revision ids are sequential and readable** (`0001`, `0002`, ...: `rev_id=` when generating), matching the plan's `versions/0001_initial.py`.
- **CHECK expressions are literals in the revision**, never built from the enums: a revision must mean the same thing after the enums change.
- **`StoreAdapter.upgrades_automatically` and `database_file()`** carry the per-backend migration behaviour (AD14 in `docs/contributing/architecture/adapters.md`), with defaults so plugins keep working (AD9).
- **The start-up check closes its connection before upgrading:** on SQLite the open transaction (`BEGIN IMMEDIATE`) holds the write lock the upgrade needs.
- **Messages say what changed:** `created dbtx's tables in <uri> (revision 0001)`, `upgraded <uri> from revision X to Y`, `<uri> is already at revision X (head)`, `created schema 'x'`. The start-up checks print the first two as warnings (an implicit change).
- **An unknown revision is always refused** (start-up, `init`, `upgrade`): "migrated by a newer dbtx".
- **`dbtx db upgrade` on an empty database creates the tables** (Alembic from base); on Postgres it refuses a missing `DB_SCHEMA` with `run dbtx db init` rather than creating it, so creating a schema stays `init`'s job.
- **`dbtx db status` never creates anything:** a SQLite file that does not exist is reported from `database_file()` without opening the store.

## Deviations from the plan

See the Phase 3 status block in the plan: no `include_schemas`; adapter members instead of a SQLite branch; `status` exit codes and dbt's real default clean target; SQLite auto-upgrade still behind `ENFORCE_DB_REQUIREMENTS` for dbt commands; the `store` fixture uses `create_all` + stamp.

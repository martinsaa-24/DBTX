# What happens when a command runs

Step by step, for platform mode and standalone mode. Which commands and options exist
in each mode is in [usage.md](usage.md), what each command does and does not do in
[commands.md](commands.md); the design behind it is in
[orm_implementation_plan.md](../agentic/orm_implementation_plan.md).

**Exit codes:** `0` success; `1` dbt reported failures (failed tests or models), or a
report failed to render; `2` a configuration or start-up problem, or an error dbt could
not recover from. Every exit 2 marked "before dbt starts" below means dbt never ran and
nothing was written.

## Platform mode: `dbtx build`

```console
cd /srv/dbtx && dbtx build --project-dir jaffle-shop
```

### 1. Configuration (before dbt starts)

1. dbtx's own flags are taken out of the command line (`--db-uri`, `--platform-dir`,
   `--job-id`, ...); dbt never sees them.
2. The mode is decided (platform root from `--platform-dir`, or the current directory
   holding `dbtx.conf`).
3. The project folder is resolved: a direct child of the platform root, holding
   `dbt_project.yml` and no `dbtx.conf` of its own. dbtx passes it to dbt as an absolute
   `--project-dir`, with `--profiles-dir` set to the same folder.
4. `dbtx.conf` is read; each option is resolved CLI > file > environment, and checked.
5. Required for a recorded command: `DB_URI` (unless `--db-backend disabled`) and
   `LOG_ROOT_LOCATION`.
6. Guard G1: no other folder on this platform declares the same dbt `name:`.

Any problem → exit 2, naming the option and where its value came from.

### 2. Start-up checks (before dbt starts)

1. Connect to the database; check the server version.
2. Check the schema revision, on every backend: a SQLite file that does not exist →
   exit 2 with `run dbtx db init`, before connecting (so no empty file is created;
   in-memory SQLite has no file); no dbtx tables → exit 2 with `run dbtx db init`; behind this dbtx's revision → exit 2 with `run dbtx db upgrade`. Schema
   changes are deliberate: nothing else creates or migrates the tables, SQLite included.
3. Guard G2: the dbt project name is claimed for this folder in the database (or
   already is). Owned by another folder → exit 2.

### 3. The run folder (before dbt starts)

1. The job id: `--job-id`, or a new one generated by dbtx. `DBTX_JOB_ID` in `--vars` →
   exit 2. (Checked with the configuration, step 1.)
2. The run folder: `<LOG_ROOT_LOCATION>/<project name>/<date>/<hour>/<job id>/` (UTC).
   It already exists → exit 2 (checked with the configuration; created only now, after
   the start-up checks passed, so a failed check leaves nothing behind).
3. The warm partial-parse cache (`<project>/target/partial_parse.msgpack`, from
   `dbtx warm-cache`) is copied into the run folder. Without one, dbt parses in full.
4. Every dbt invocation of this command gets `--target-path` and `--log-path` pointing
   at the run folder, and the environment variable `DBT_ENV_CUSTOM_ENV_DBTX_JOB_ID`.
   A `--target-path` or `--log-path` of the user's own → exit 2.

### 4. dbtx prepares the build

1. The project's report templates are resolved.
2. dbtx runs `dbt parse` itself (using the copied cache), and checks every report
   definition against the parsed project. An invalid report → exit 2, before anything
   is built.
3. If the project fails to parse, dbtx runs the user's command so dbt reports the error
   in its usual format. That run is recorded as a `failure` with dbt's message; no
   node or report in the database is changed.
4. `dbt ls` resolves the selection, to know which reports this run renders.

Neither the internal parse nor `ls` is recorded.

### 5. The build

dbt builds, handed the manifest dbtx parsed. While it runs:

- On dbt's first event, the run is recorded as started: the invocation (dbt's
  invocation id, command, job id, user, host, ...), the project's nodes and reports,
  and a `pending` row for each report this run renders.
- Each report renders as soon as its exposure is ready and its tests have passed, on
  the dbt thread that made it ready. Every change (`running`, then `rendered`,
  `skipped` or `error`) is recorded as it happens.

When dbt returns, the run is finished in one transaction: a result for every node
(status, timings, message, compiled SQL and target relation), the target
and adapter dbt resolved, the end time, the overall result, the run folder
and the hash of the manifest dbt wrote in this run.

Recording never changes the run: if a database write fails, dbtx prints one
`dbtx: run history not recorded (invocation ...)` warning and carries on.

### 6. After the build

1. The run's `reports/` folder (when it rendered any) is copied into the project's
   docs site, `<project>/target/reports/`.
2. The docs site is patched with this run's results (`dbtx docs patch`, run
   internally): run status, timings, job id, history and embedded reports. No docs site
   yet, or no `run_results.json` (`--no-write-json`): a note, nothing patched. A failed
   patch is a warning; it never changes the exit code.

### 7. Exit

dbtx prints its report summary and exits with dbt's code, or 1 if a report failed to
render.

## Platform mode: other commands

- **`run`, `test`, `seed`, `snapshot`, `run-operation`, `source freshness`** are passed
  to dbt as typed, with steps 1–3, the recording of step 5 and step 6.
  dbt parses for itself (using the copied cache). The project's nodes are stored from
  the manifest this run wrote; reports are stored only by `build` and `compile`.
- **`compile`** follows `build` without rendering: reports are validated and their
  SQL written; the run is recorded with no renders.
- **`docs generate`** runs in its own run folder, then copies
  `index.html`, `manifest.json` and `catalog.json` into `<project>/target/`. Run
  `dbtx docs install` afterwards to put dbtx's overlay back
  ([docs_refresh.md](docs_refresh.md)).
- **`dbtx warm-cache`** parses the project into `<project>/target/`
  writing only the partial-parse cache (no `manifest.json`, so the docs site is
  untouched). Not recorded. Run it after deploying or merging new code.
- **`ls`, `debug`, `deps`, `show`, ...** go to dbt as typed, with the project and
  profiles folder set. Not recorded, no database connection, no run folder.
- **`dbtx db ...`** works on the database directly; `db load` imports a plain dbt run's
  artifacts.

## Standalone mode: `dbtx build`

```console
cd jaffle-shop && dbtx build --standalone-mode
```

1. dbtx's flags are taken out of the command line. Database flags, `--config-file`,
   `--log-root-location` and `--job-id` contradict standalone mode →
   exit 2. `DBTX_*` environment variables are ignored
   (listed by `dbtx config`). No config file is read.
2. No database, no guards, no start-up checks; nothing is recorded.
3. dbt finds the project and profiles its own way; dbtx adds nothing to the command
   line.
4. Outputs go to the project's `target/` and `logs/`, as with plain dbt. Run folders
   are a platform feature: `--log-root-location` and `--job-id` contradict standalone
   mode → exit 2. To name a job, pass `--vars '{DBTX_JOB_ID: ...}'`.
5. dbtx prepares and builds exactly as in platform mode (steps 4 and 5, without the
   recording) and prints its report summary.
6. The docs site is not touched: run `dbtx docs patch --docs-loc ... --run-loc ...`
   yourself.
